# 多Agent代码协作助手项目企划

## 项目目标

做一个本地优先的多 Agent 代码协作助手，用来辅助个人项目开发。它不是一次性把所有工作交给 AI，而是把需求拆成可控步骤，让不同 Agent 分别负责方案、行动、验收和监督。

第一阶段目标是跑通最小闭环：

- 能读取项目规则、需求文档和当前 Git 状态。
- 能生成本轮任务的上下文包。
- 能按角色调用 AI。
- 能记录执行过程、结果和待确认问题。
- 不直接写入主知识库，不越权删除、移动、上传、部署或推送。

## 核心角色

- 方案 Agent：拆解任务、提出实现方案、列出风险。
- 监督 Agent：审查方案和执行结果，决定继续、返工或请求人工确认。
- 行动 Agent：按已确认方案修改代码或生成文件。
- 验收 Agent：运行检查、测试和人工可读的验收总结。

第一版不要求每个 Agent 使用不同 API Key。多个 Agent 可以先共用一个 AI 接口，通过不同 `system_prompt`、上下文、参数和工具权限区分职责。

## 多 AI 接入思路

项目不把 DeepSeek、OpenAI、Claude、本地模型等写死在业务流程里，而是做一层统一的 provider 配置。

示意结构：

```text
任务
  ↓
调度器 / 监督 Agent
  ↓
角色 Agent
  ↓
统一 AI 调用函数
  ↓
DeepSeek / OpenAI / Claude / 本地模型 / 其他兼容接口
```

每个 provider 只负责说明：

- `base_url`：接口地址。
- `model`：使用的模型名。
- `api_key_env`：从哪个环境变量读取密钥。
- `request_format`：请求格式是否兼容 OpenAI 风格。

每个 Agent 只选择 provider 和角色提示词，不直接管理密钥。

## 上下文压缩与上下文包

上下文压缩的核心原则：不要让 AI 记住所有聊天记录，而是把项目事实整理成可重复读取的任务上下文包。

聊天记录不能当数据库。项目长期事实应该保存在项目文件、日志和知识库中；每次任务开始时，只抽取当前任务必须知道的内容，生成一份短的 `context-pack` 交给 Agent。

上下文流转：

```text
长期知识库 / 项目文档 / Git 状态
  ↓ 提取
任务上下文包 context-pack
  ↓ 传给 AI
Agent 执行
  ↓ 产出
执行日志 / 决策 / 踩坑
  ↓ 经过确认后再沉淀
```

上下文包固定包含：

- 任务目标：本轮到底要完成什么。
- 必须遵守：项目规则、权限边界、禁止事项。
- 当前相关文件：只列和本轮有关的文件路径和摘要。
- 已知风险：容易踩坑的点、未确认事项。
- 本轮允许范围：允许读什么、写什么、执行什么。
- 当前状态：已完成、未完成、阻塞、下一步。

示例模板：

```md
# 任务目标

...

# 必须遵守

...

# 当前相关文件

...

# 已知风险

...

# 本轮允许范围

...

# 当前状态

...
```

多个 Agent 之间不直接共享完整聊天记录，而是共享同一份上下文包，再叠加自己的角色提示词：

- 方案 Agent 看目标、限制和相关文件摘要。
- 行动 Agent 看确认后的方案、允许修改的文件和执行边界。
- 验收 Agent 看改动说明、测试结果和风险清单。
- 监督 Agent 看全流程摘要，决定通过、返工或请求人工确认。

长任务每轮结束都要生成状态快照：

```md
# 已完成

...

# 未完成

...

# 当前阻塞

...

# 下一步

...

# 不要重复做

...
```

第一版先使用固定目录、关键词匹配、文件摘要和模板生成上下文包。暂时不引入向量数据库。等项目文档和代码量大到普通关键词匹配不够用时，再考虑向量检索。

## 目录规划

```text
product-docs/        人写的需求、规则、企划和关键决策
dev-vault/pending/   实验经验和候选沉淀，确认后才能进入主知识库
logs/context-packs/  每次任务生成的上下文包
logs/runs/           每轮 Agent 执行记录
src/                 程序源码
tests/               自动化测试
```

主知识库默认只读。任何要写回主知识库的内容，都必须经过人工确认。

## 第一版实现顺序

1. 写一个最小 AI 调用函数，先跑通一次请求和响应。
2. 建一个 Agent 配置字典，用不同提示词区分角色。
3. 做命令行选择，让用户能手动指定运行哪个 Agent。
4. 生成固定模板的 `context-pack`。
5. 做多 Agent 顺序协作：方案、监督、行动、验收、监督。
6. 把 provider 抽象出来，再接入多个 AI。
7. 增加权限层，限制文件写入、命令执行和知识库同步。

## 权限边界

AI 只能提出建议和产出内容，不能自己决定高风险操作。

以下操作必须由程序权限层拦截，并在需要时请求人工确认：

- 删除、覆盖、批量移动文件。
- 写入主知识库。
- 安装软件或依赖。
- 上传、推送、部署。
- 访问或保存密钥、令牌、Cookie。
- 修改生产系统或真实业务数据。

项目的安全原则是：Agent 可以自动协作，但关键权限必须由人和程序共同控制。
